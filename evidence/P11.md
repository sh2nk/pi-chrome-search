# P11 — M11: the Allow prompt cannot be missed

Date: 2026-11-06
Owner: orchestrator
Verdict: **PASS** on V11.2–V11.6; **V11.1 reproduced live as a failure condition during P9 and covered by
the new wait offline + against a silent endpoint**. A fresh-Chrome re-reproduction is **BLOCKED by rule**
(see the note in V11.1), not by code.

Plan: `PLAN-v2.md` §4 (P11-A..P11-C). The user's report that started this phase: *"я не всегда вижу что в
браузере появляется промт и не всегда успеваю прокликать allow"*. The mechanism is a WebSocket handshake
that Chrome completes only after the click; the old 5 s/7 s budget expired first and reported a dead browser.

## What landed

- **L3 (P11-A)** `config.cdp.attachWaitMs` (default 60 000, `0` = pre-P11 single attempt). The connector
  retries the handshake with a short per-attempt timeout, reports progress through
  `onAwaitingAllow(info)`, and ends with the new frozen code **`E_CDP_AWAITING_ALLOW`** (retryable) instead
  of `E_CDP_UNAVAILABLE`. A refused socket (`ECONNREFUSED`/`ENOTFOUND`/`EHOSTUNREACH`/`EAI_AGAIN`) still
  fails immediately, so a closed browser never costs a 60 s wait.
- **L0** progress line `waiting for the Allow prompt… 12s — <brand-aware hint>` and OSC 9 + OSC 777
  escapes, emitted **only when stdout is a TTY and the run is not `--json`**; JSON runs get plain text on
  stderr. `--watch` extends the budget to 5 minutes for a second terminal.
- **L1** `src/runtime/notify.ts`: one notification per session, `urgency=critical`, `-t 0`; Linux ladder
  `notify-send` → `gdbus` → `dbus-send`, macOS `osascript`, Windows `powershell` toast. Every binary comes
  from `capability()` (PO1); every failure is swallowed into a result.
- **L2** `src/cdp/raise.ts`: one best-effort focus attempt through a static adapter table
  (`wmctrl` → `xdotool` → `kdotool` → `hyprctl eval` → `hyprctl dispatch` → `swaymsg`; `osascript` /
  `powershell` on the other OSes), 1 s each, exact command logged, `raise: unavailable` is normal.
  `window.raiseOnPrompt: "auto" | "never"` (default `auto`); nothing launches a browser, opens a window/tab
  or URL, or installs anything.
- **S3 spike closed**: `evidence/P11-spike.md` (2026-11-06). One CDP connection, one
  `gio launch …/google-chrome.desktop`: Chrome opens and focuses a **second window** instead of activating
  the running one (window count 1 → 2, a new `chrome://newtab/` target, focus moved), so the plan's draft
  rung stays out of the ladder and the comment in `raise.ts` is now backed by a measurement. The same file
  records the degradation matrix (OS × desktop × with/without helpers) and the macOS/Windows equivalents
  on paper.
- **`src/runtime/attention.ts`**: the coordinator. One notification + one raise per session, throttled
  progress, `flush()` for the doctor, `oscNotification()`/`renderAwaitingAllow()`.
- **Doctor**: `CdpStatus` gains `awaiting_allow`; the connect budget includes `attachWaitMs`; a fix/timeout
  is reported with the wait duration, notification adapter and raise adapter. `web_doctor`/CLI share it.
- **Audit**: R3/R13 now permit `child_process` only in the declared adapters (`notify.ts`, `raise.ts`,
  and later `extract/pdf.ts`), with self-test guards for both the exemption and the control file. R11 now
  parses `P10+` rows (it silently skipped them before).
- **Tests**: `tests/unit/notify.test.ts`, `raise.test.ts`, `attention.test.ts` (new), 5 browser wait tests,
  3 CLI/doctor tests, schema + config updates. Total `890` offline tests.

## V11.1 — a pending Allow waits, reports progress and exits with `E_CDP_AWAITING_ALLOW`

The condition was **observed live twice during P9** (2026-11-06, 13:26 and 13:28 runs): two connect
attempts expired and the log claimed `connect failed`/`reconnect failed` while the same process then
reported `cdp: ok`. That is the defect this phase makes impossible to mislabel.

Offline reproduction of the state machine (a `connectSession` that hangs until the budget expires):

```
node --test tests/unit/browser.test.ts
```

```
✔ P11: a pending Allow is waited out and the same connect call succeeds
✔ P11: an expired wait is E_CDP_AWAITING_ALLOW, not a generic CDP failure
✔ P11: attachWaitMs 0 keeps the old single-attempt behaviour
✔ P11: a refused socket fails immediately — no pointless 60 s wait
✔ P11: the awaiting hint names the detected browser family, not always Chrome
```

Live run against a **silent endpoint** (a TCP server that accepts and never answers — the same shape as an
unanswered prompt; this is a simulation, not Chrome), with `attachWaitMs: 7000`:

```
node -e 'require("node:net").createServer(()=>{}).listen(9877, "127.0.0.1")' &
node src/cli/doctor.ts --json --no-probe --config /tmp/p11-sim.json
```

```
waiting for the Allow prompt… 3s — open chrome://inspect/#remote-debugging (edge://, brave:// or
chromium:// for the other Chromium-family browsers), tick "Discover network targets" and click Allow,
then retry; or set PI_CHROME_CDP_WS=ws://127.0.0.1:<port><path>
attention: waited 8s · notify notify-send · raise hyprctl-eval
```

```
verdict=blocked cdp=awaiting_allow code=E_CDP_AWAITING_ALLOW

         may be waiting in the browser window
```

Exit 2, no `--fix` action, no Chrome touched, no profile read/write.

**Why the real prompt was not re-created:** forcing it again means restarting Chrome (forbidden, AGENTS §2)
or toggling the Allow off in `chrome://inspect` (which would leave the user's session unusable mid-gate).
The wait is therefore proven offline and against a live silent socket; the real condition is the one P9
already recorded. Recorded as a BLOCKED caveat, not a waived gate.

## V11.5 — L0 escapes are emitted only on a TTY, never into logs/JSON/CI

```
✔ P11: OSC escapes go to a TTY stdout only, never into JSON
```

With `isTTY: true` and text mode, stdout contains `\u001b]9;` and `\u001b]777;notify;`; with `--json` the
escapes are absent from stdout (which still parses) and the progress text goes to stderr as plain text.
`oscNotification()` strips `BEL`/`ESC` from the message itself, so a hostile hint cannot break the sequence.

## V11.6 — no profile access, no CDP before Allow, brand-aware hint

- The wait happens **before** any CDP command: discovery reads `DevToolsActivePort` (a file), then the
  connector retries `Target.attachToTarget`'s transport only after the handshake. No profile file is read or
  written by `notify.ts`/`raise.ts`/`attention.ts` (they use `capability()` and window identity strings).
- The hint is built with `cdpAllowHint(brand)`; a brave profile yields `brave://inspect/#remote-debugging`
  and never mentions `chrome://` (`P11: the awaiting hint names the detected browser family`).

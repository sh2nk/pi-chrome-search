# P8 — M8: the AI summary is real, or it is absent

Date: 2026-11-06
Owner: orchestrator
Verdict: **PASS** (V8.1–V8.5)

Plan: `PLAN-v2.md` §4 (P8-A..P8-D) and §3 spike S4. The user-visible defect: `ai:yes` was printed for a
Google AI block whose whole text was the lead echo `Ответ в режиме ИИ, исходный запрос: "…"`. This phase
makes the state explicit (`answer`/`lead`/`none`), waits for streaming prose, and never lets a short or
echo-only text be an answer.

## What landed

- **Contract** (`contract: ai states`): `AiState = "answer" | "lead" | "none"`, `AI_ANSWER_MIN_CHARS = 200`,
  `AiSummary.state`, `AiProbe`, optional `Engine.ai` (`probe`, `expand`), `SerpTimings.aiWaitMs`. Additive
  only; adapters that omit the hooks simply never wait.
- **`src/cdp/ai-wait.ts`** (new): bounded `waitForAi(page, ai, options)`. Returns on the first probe with
  ≥`minChars` of answer prose; keeps waiting while a lead is present; stops after a 1.4 s grace when the
  page has no AI block, so a summary-less search does not pay the 6 s budget. Clock/rng/abort seams are the
  same as `waitForMarker` (exported from `cdp/humanize.ts`).
- **Adapters**: Google (`aiAnswerText` now returns `{text,state}`, one optional expand via
  `findAiExpandTarget`/`expandGoogleAiOnce`), DuckDuckGo (`readAssist`), Yandex (`readAi`, reuses the
  existing `expandAiSummaryOnce`). Each exposes an `aiOnly` probe mode of the *same* in-page function, so a
  probe cannot disagree with extraction (asserted for every fixture).
- **`extract/compact.ts`**: re-derives the state from text and query (`ai:yes` needs ≥200 chars and is never
  a query echo), prefers an answer from any engine over a lead, prints `ai:lead` for a lead with no answer
  line, and drops the `yes` header when the AI block loses its space.
- **`web_search`**: waits only for `summary:true` and only when the adapter has a probe; opt-in
  `search.aiExpand` (default `false`); saves an `AI_TIMEOUT` artifact when the wait ends without an answer;
  reports `aiState`, `aiWaitMs`, `aiChars` in `details` and writes one `kind:"search"` row to
  `decisions.jsonl`.
- **Config**: `search.aiWaitMs` (default `6000`, `0` disables), `search.aiExpand` (default `false`).
- **Fixtures**: `google-ai-lead` (derived from the real `google-ai`), `ddg-assist-lead` (derived from
  `ddg-assist`); the absent state reuses `google-no-ai`/`ddg-empty`. Derived files are labelled as such in
  `meta.json` and in `research/FINDINGS.md` §12.
- **S4 probe**: `research/probes/10-ai-stream.mjs` (one navigation, one query, adapter probe timeline).

The guard lives in `compact.ts::aiStateOf` and is applied to every candidate, including a hand-built
`RawSerp`: empty text → `lead`; text equal to the query (whitespace/case-insensitive) → `lead`; text under
200 chars → `lead`; declared `none` → `none`. The test above feeds `answer`-declared candidates with a
short text, the exact query, a padded/upper-cased query, and 199 chars; all render `ai:lead` with no line.

## V8.4 — added latency, and `summary:false` costs nothing

| Engine | state | `aiWaitMs` | Note |
|---|---|---|---|
| DuckDuckGo | answer | 7 ms | answer already on the page at the first probe |
| Yandex | answer | 2 240 ms | the card itself streamed in; the wait returns on the first ≥200-char probe |
| Google | none | 1 406 ms | no AI block: the wait stops at the 1.4 s grace (V8.4 ceiling 1.5 s) |

`summary:false` never calls the probe (offline assertion `summary:false never probes and reports aiState
none with zero wait`), and `search.aiWaitMs: 0` probes once and returns (`aiWaitMs:0 probes once and
returns`). The none-grace constant is 1 400 ms rather than 1 500 ms on purpose: probe round-trips and the
jittered poll land on top of the grace, and the live measurement (1 406 ms) shows the margin is real.
